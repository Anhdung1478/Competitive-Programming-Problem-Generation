# Write `generator-config.md`

This file is the bridge between the problem specification, test script, and generator implementation.

Do not write generic filler. Every section must be specific to the current problem.

## Required sections

### 1. Input schema

Create a table with:

- field/symbol;
- type;
- scope;
- legal range;
- relation to other fields;
- whether it repeats per test case.

Include global multi-test sum constraints.

### 2. Structural invariants

Examples:

- array length matches `n`;
- permutation contains each value exactly once;
- graph has no loops;
- graph is connected;
- tree has exactly `n-1` edges;
- intervals satisfy `l <= r`;
- string uses only a given alphabet.

Only include invariants supported by the specification.

### 3. Subtask table

For every subtask, write:

- score;
- numeric limits;
- structural restrictions;
- which restrictions differ from full constraints;
- generator logic needed to guarantee the subtask.

### 4. `rate` interpretation

Define exactly how `rate` scales the instance.

General rule:

- `rate` controls target magnitude relative to the chosen subtask;
- it must not break lower bounds or structural relations;
- coupled quantities (`n`, `m`, total lengths, query counts) may need separate derived rates;
- clamp values to legal ranges after scaling;
- do not simply multiply a value when that would destroy a special constraint such as `m=n-1`.

Document per-variable behavior for this problem.

### 5. Generator options

Document every option that may appear in `test-script.txt`.

Always:

- positional `seed` immediately after the generator name;
- named option `subtask`;
- named option `rate`.

The seed is not written as `--seed` and does not need to be treated as a normal named generator option.

When applicable:

- `numtest`;
- structure/profile options such as `tree-type`, `density`, `value-profile`, `answer-profile`.

For each option specify allowed values and effect.

### 6. Generation profiles

List profile families needed for the problem, for example:

- minimum/degenerate;
- random;
- near-maximum;
- all-equal;
- monotone;
- duplicate-heavy;
- sparse/dense;
- line/star/focused tree;
- disconnected/connected if legal;
- answer exists/does not exist;
- arithmetic boundary values;
- worst cases for the intended algorithm.

Explain why each family matters.

### 7. Subtask-specific generation

Call out any subtask that cannot be generated by merely shrinking full constraints.

Examples:

- `M = 2`;
- graph is a tree;
- `K = 0`;
- values are prime;
- array is a permutation;
- no repeated edges;
- only one query type.

Write exact enforcement logic.

### 8. Coverage plan

Map profiles to subtasks and rough frequencies.

Make sure the eventual 100-test default has enough:

- boundary tests;
- high-rate tests;
- random tests;
- adversarial tests;
- special-structure tests.

### 9. Specialized skills

Name the specialized generator skills that `polygon-gentest` should load.

### 10. Generator assertions

List conditions `gentest.cpp` should `ensure(...)`/assert before printing.

## Rule against hidden assumptions

If generator behavior requires choosing an unspecified property, stop and ask the user.

Examples:

- assuming a graph is simple;
- assuming `a_i > 0`;
- assuming a solution always exists;
- assuming test cases are independent with no total bound.
